# Story 4.3: SubtaskView Intégré dans TaskView

## Status
Draft

## Story

**As a** project manager using Archon-TRAXIS,
**I want** Subtasks to be integrated directly within the Task view,
**so that** I can manage task breakdown and subtask details without leaving the Task context.

## Acceptance Criteria

1. **Subtask Integration**: Subtasks are displayed and managed within the existing TaskView
2. **Subtask CRUD Operations**: Full Create, Read, Update, Delete operations for Subtasks within Tasks
3. **Subtask Status Management**: Support Subtask statuses (todo, doing, review, waiting, done)
4. **Task Progress Calculation**: Task progress automatically calculated from Subtask completion
5. **Hierarchical Display**: Clear visual hierarchy showing Task → Subtask relationships
6. **Subtask Assignee Support**: Support assigning Subtasks to different team members
7. **Drag & Drop Support**: Enable reordering Subtasks within Tasks
8. **Collapsible Subtasks**: Ability to expand/collapse Subtask lists for better UX

### Previous Story Insights
- Epic 1 (BDD) established that Subtasks reuse the `archon_tasks` table with `parent_task_id`
- Epic 3 (MCP) added Subtask tools: `find_subtasks()` and `manage_subtask()`

- Architecture decision: One table `archon_tasks` for both Tasks and Subtasks

### Data Models
**Extended Task Interface** (based on existing + Subtask support):
```typescript
// Extend existing Task interface
interface Task {
  id: string;
  story_id: string;
  parent_task_id?: string; // For Subtasks
  title: string;
  description: string | null;
  status: 'todo' | 'doing' | 'review' | 'waiting' | 'done';
  assignee: 'User' | 'Archon' | 'AI IDE Agent';
  task_order: number;
  progress?: number; // calculated from child Subtasks
  subtasks?: Task[]; // Array of child Subtasks
  created_at: string;
  updated_at: string;
}

// Helper type for Subtasks
type Subtask = Task & { parent_task_id: string };
```
[Source: Epic 1 BDD implementation + existing Task types]

### API Specifications
**Existing Task Endpoints** (to be extended):
- `GET /api/stories/{story_id}/tasks` - Now returns Tasks with nested Subtasks
- `POST /api/tasks` - Creates Task or Subtask (based on parent_task_id)
- `GET /api/tasks/{task_id}` - Returns Task with Subtasks
- `PUT /api/tasks/{task_id}` - Updates Task or Subtask
- `DELETE /api/tasks/{task_id}` - Deletes Task or Subtask

**New Subtask-specific Endpoints**:
- `GET /api/tasks/{task_id}/subtasks` - Get Subtasks for Task
- `PUT /api/tasks/{task_id}/subtasks/reorder` - Reorder Subtasks

All endpoints maintain existing ETag caching and patterns.
